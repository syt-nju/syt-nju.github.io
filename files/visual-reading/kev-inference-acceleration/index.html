kev 的推理加速：从 CUDA Graph 基本原理到超参边界

为什么一个开关能让吞吐差一倍、背后和主流推理引擎走了哪条相反的路，以及作为后训练研究员改数据长度和调参时该盯住什么。

读者 后训练研究员 实测硬件 NVIDIA H20 · 昆仑芯 P800（96 GB） 模型 Kev-Qwen3.5-0.8B（混合注意力）

TL;DR

CUDA Graph 治的不是「GPU 算得慢」，是「CPU 派活慢」。kev 一次前向要往 GPU 派约 2,000 个小算子（kernel），而输入只有几百个 token——GPU 早算完了，CPU 还在逐个派下一道指令。把整串指令提前录成一张图、一次下发，省掉的是指令之间的空等缝隙。

代价是地址和张量形状一并锁死。想塞进变长请求，主流引擎选「多条首尾连成一条 + 到注意力处把图切开」，kev 则选「一条占一行补齐等长 + 整趟前向连着线性注意力录进同一张图」。十个服务超参，本质上全在规定这块固定缓冲的准入线、长宽预算和淘汰策略。

作为后训练研究员最该记住两件事：改长提示词前先看有没有跨过 1024 的准入悬崖（我们线上最长那道题已经走到 913）；而在 kev 里关掉图开关会连带关掉跨请求合批——P800 上吞吐掉回一半就是这么摔的。

01什么时候有用：省的是派活的缝隙，不是算力

CUDA Graph 不会让任何一个 kernel 算得更快。它成立的唯一前提是：GPU 经常闲下来等 CPU 派下一道活。

PyTorch 默认是逐个发射（eager 模式）：Python 走到一行算子，CPU 就现场检查形状、算需要派多少并行线程、往显卡队列塞一条指令，把一个 kernel（GPU 上的小计算函数，一次矩阵乘或一次逐元素相加各是一个）交出去。单次派活只要几微秒，但架不住两个条件同时撞上：

  • 派活次数极多、而且外层 Python 包装重：kev 跑一趟前向要发约 2,000 个 kernel；Qwen3.5 里的线性注意力层（Gated DeltaNet）调用第三方算子库时，光算子外面的 Python 包装代码每层就要吃掉约 1 毫秒 CPU。
  • 每次真算的活极轻：模型只有 0.8B，序列只有几百个 token，单个 kernel 在 GPU 上几微秒就跑完了——结果就是 GPU 干完一件停一下，全程在等 CPU 下单。这种状态叫卡在发射上（launch-bound）；反过来训练时大 batch 长序列把 GPU 喂饱，叫卡在计算上（compute-bound），那时开图几乎没有收益。
对照主流引擎 · 为什么别人只给解码开图，kev 却给预填充开图

生成式推理分两段：预填充（prefill）一口气读完整段输入，解码（decode）之后每次只算 1 个新 token。vLLM 和 SGLang 主要给解码开图——每步 1 个 token，GPU 一下就算完，正是典型的「卡在发射上」；而预填充一次吃几千 token，GPU 本来就忙得过来，所以它们长期默认不对预填充建图。

kev 恰好处在夹缝里：它是判别式决策模型，只有预填充、不吐生成 token；但 0.8B 模型配几百 token 的输入，让它的预填充轻得像别人的解码。后面所有「kev 为什么不照搬 vLLM 的做法」，根子都在这一句。

把两千次派活合成一次提交，靠的是「预热 → 捕获 → 重放」三步；而一切使用限制都来自第二步录下了具体的显存地址。

  • 为什么第 ① 步预热省不掉：算子库第一次遇到某个尺寸时，会现场编译代码、试跑几种实现挑最快的、向显卡驱动要显存。这些一次性动作都会让 CPU 停下来等 GPU，一旦混进第 ② 步就会直接导致录制报错。

03变长请求怎么塞进死形状：两条路与一个二选一

真实请求长短不一，而每录一张新图大约要花 0.4 秒。想用少数几张图接住所有流量，业界只有两种摆法——它们在 Qwen3.5 这种混合架构上恰好互斥。

训练时大家熟悉的 sequence packing 给出了第一条路：假设来了三条请求，长度分别是 3、2、5 个 token，把它们首尾相接排成一条长 10 的队伍 [A A A | B B | C C C C C]，只在整条队伍末尾补少量假 token 凑够总长度档位。vLLM 和 SGLang 走的就是这条路——图的尺寸只需要按「总 token 数」这一个数字分档，启动时顺着一把固定梯子（比如 1、2、4、8……）一次性全录完。

但连成一条之后，队伍中间的竖线没了。对层里绝大多数计算来说这毫无影响——MLP、两个 RMSNorm、残差相加，以及算 q/k/v 的线性投影，每个 token 的输出只看它自己的向量、不看邻居，排成一排照算不误。唯独到了注意力与线性注意力（DeltaNet），为了算 B 时不把 A 的尾巴混进来，你必须额外递给 kernel 一串分界点位置 [0, 3, 5, 10]（意思是 0–3 归第一条、3–5 归第二条、5–10 归第三条）。

vLLM 跑 Qwen3.5 时照样连成一条，也照样递这串分界点去防串味——kernel 走到 3 和 5 会自己重置卷积窗口、换上对应请求的初始状态。真正的代价出在下一步：线性注意力的预填充不是一把算完，而是把每条序列切成固定长度的小段，读完一段更新一次状态矩阵。点一下下面四个按钮就能看到麻烦在哪：

  • 为什么摆法一录不进图：vLLM 的图是按「总 token 数 = 10」这一档提前录好的，但同样 10 个 token，来 1 条切 3 段，来 2 条切 4 段，来 10 条切 10 段——描述分段起止的那组数组长度跟着乱跳，而且是在 CPU 上按本批分界点现算出来的，装不进尺寸写死的图里。
  • vLLM 的解决办法：每到注意力 / DeltaNet 层就把图断开，这一层退回逐个发射，夹在中间的逐 token 计算（MLP、RMSNorm、qkv 投影）才录进图里。N 层模型由此被切成 N + 1 张小图。
  • 为什么摆法二能整趟录进一张图：kev 让每条序列独占一行、补齐到同一行长。每行从头到尾都是同一条请求，根本用不上分界点；总段数严格等于 行数 × 每行段数，只要行数和行长固定，内部工作量就完全锁死。
一句话看懂两家的取舍：「连成一条省 padding」和「把 DeltaNet 一起录进图里省派活开销」两件事只能二选一。vLLM 面向通用长短混杂流量，拼起来省下的 padding 大头远比切开图漏掉的那点发射时间值钱；而 kev 是 0.8B 短序列，最拖后腿的恰恰是每层 DeltaNet 外面那约 1 毫秒的 Python 包装——要是把 DeltaNet 切出图外，开图就白忙活了大半。所以 kev 宁可放弃拼接，也要保住整趟前向一刀不切全进一张图。

04kev 怎么把浪费压住：分桶与同题合批

选了「一条一行向上补齐」，就得正面回答两个问题：档位怎么切才不浪费太多 padding？同一批里的长行和短行怎么避免互相拖累？

第一招：每个 2 的幂区间再等分 8 档

如果只按 2 的幂设档（512 下一档直接跳 1024），一条 513 token 的序列就得陪跑近一半空位；反过来每 16 个 token 设一档，图的张数又会爆炸。kev 的折中是先看长度落在哪个 2 的幂区间，再把那个区间等切成 8 档：256–512 之间每 64 一档，512–1024 之间每 128 一档（只有 640 / 768 / 896 / 1024 四个落点），1024–2048 之间每 256 一档。这样任意长度补齐的相对浪费封死在 25% 以内，而总档位数只按对数增长。

  • 超限不是斜坡，是悬崖：一旦某条请求跨过 1024，它不会报错、也不会只慢一点点，而是整条请求被拒之图外、退回逐条串行（9.12 req/s 那条平线）。往提示词里塞新示例或改模板前，必须先算这一笔账。
  • 我们的三道题分别落在哪：913 → 1024，698 → 768，271 → 320。

第二招：把一条请求拆成「状态趟 + 同题问题行趟」

落到我们真实的评测数据上，kev 处理一条请求涉及三样东西：

  • 状态（state）：被判断的那条用户查询本身，比如一条约 30 字、24 个 token 的真实用户短查询，每条请求各不相同。
  • 问题行（row）：针对这条查询提问的某一道题的完整提示文本，一道题占一行。我们一共问三道固定题，实测长度分别是 913 / 698 / 271 个 token，600 条请求共用同一份题面，一字不差。
  • 状态槽（bank）：显存里预留的一排固定格子（默认 16 格），用来暂存刚算好的查询状态，供后面的问题行按格号取用。

推理分两步走：状态趟先把一批查询（每条 24 token）读一遍，算出各层的注意力 KV 和 DeltaNet 状态矩阵存进状态槽，实测仅需 8.87 ms；紧接着问题行趟让每道题按格号接上各自的状态往下算答案，实测 70.28 ms——近九成算力都花在固定题面上。

更妙的是分组方式。注意缓存里虽然存着好多张不同规格的图，但「一趟前向」一次只能选其中一张跑，输入必须是一个规整的长方形矩阵——同一个矩阵里不可能第 1 行宽 1024、第 2 行宽 320，凡是塞进同一趟的行，只能全部迁就这趟最长的那一行。所以如果把 4 条请求的 12 道问题行硬塞进同一趟，就只能调 1024 宽的那张图，271 的短题也得跟着陪跑到 1024；kev 因此先按行长做动态规划分组，自动把不同请求的同一道题拆成三趟，分别去调 1024、768、320 三张不同宽度的图：

4 条请求 × 3 道题 ＝ 12 条问题行： 拆成三趟（分别调 1024 / 768 / 320 三张图）：4×1024 ＋ 4×768 ＋ 4×320 ＝ 8,448 个 token 位置 硬塞一趟（只能调 1024 这一张图）： 12×1024 ＝ 12,288 个 token 位置 （白算 45%）

拆开之后，同一趟里装的全是同一道题——不仅省了三分之一面积，而且各行本来就一样长，行与行之间连 1 个 token 的参差都没有，前面放弃拼接的唯一短板在这里顺手消失了。（反过来一旦关掉图开关，kev 退回每次只跑单条请求，把这三道长短悬殊的题硬补成 3 × 913 一起算——连分组方式都跟着退化了。）

成批明明还要补 12% 的 padding，真正省钱的大头在哪？ 高并发反而把 padding 从单条串行的 45.5% 压到了 12.2%，更把「搬 1.6 GB 权重 + 发一趟前向」的固定开销平摊了好几倍。

先看 padding 会不会随并发恶化——恰恰相反：单条串行跑时，1 条请求只有自己的三道题（913 + 698 + 271 = 1,882 个真实 token），硬塞进 3 × 913 = 2,739 的矩阵，白算 45.5% 的空位；而 8 条请求成批分桌后，每条只占 1024 + 768 + 320 = 2,112 个位置，空位反而降到 12.2%。就算换成自由变长流量，同批人越多越容易按长度排成「身高相近的几桌」，同桌身高差反而更小。

再看成批真正省下的两笔固定大头：0.8B（bf16）权重约 1.6 GB，每跑一趟前向 GPU 都得把整份权重从显存搬进计算单元一遍；行数少时计算单元根本喂不饱，耗时大头全卡在搬权重上。8 条请求逐条串行要跑「状态 1 趟 + 问题 1 趟」× 8 ＝ 16 趟前向（来回搬 25.6 GB 权重）；成批后「状态合跑 1 趟 + 三道题各 1 趟」＝ 一共只跑 4 趟（搬 6.4 GB 权重）——哪怕凑满 24 条请求，依然还是这 4 趟。多算 12% 的空位换少搬十几遍权重、少发十几趟前向，完全是零头换大头。

补进去的 padding 怎么做到绝对不污染答案？ 状态趟左填充、问题行右填充，外加一条防止 0 × NaN = NaN 的自注意保护规则。

状态趟用左填充（padding 垫在真实 token 左边）：DeltaNet 在左边的空位处看到全零输入，状态矩阵推进到第一个真实 token 时恰好还是干净的全零；普通注意力层把左侧空位从可见范围里屏蔽掉，但特意让空位自己注意自己——否则整行全被屏蔽会让 softmax 算出 NaN，而 NaN × 0 还是 NaN，事后乘零也救不回来。

问题行趟用右填充（padding 垫在末尾）：因果掩码天然让前面的真实 token 看不见末尾空位；从状态槽取出的历史状态在档位内靠右对齐，左侧未填满的槽位一并屏蔽。两套规则合在一起，保证了一条请求的答案绝不取决于同批塞进了什么邻居。

三维规格 (Nb, Lb, Sr)：为什么 kev 只能边跑边录

主流引擎把上下文切成固定大小的页块存在显存里，算注意力时按一张尺寸固定的「页号表」去取——页号表里的数字每步变，但表本身的张量形状不变，再加上请求连成了一条，所以一张图只需要「总 token 数」这一个维度，启动时就能把所有档位一次录完。

kev 没有分页（DeltaNet 的状态是每层一个固定大小的矩阵，没法按 token 切页），又是按行摆的二维缓冲，所以唯一确定一张问题行图需要三个实时算出来的数字：

  • 行数档 Nb（1, 2, 3, 4, 6, 8, 12, 16, 24, 32……）：因为行数也是矩阵形状的第一维，17 行和 18 行在图眼里是两张不同的图，不设档位图数就会翻三倍；但它没粗暴到只取 2 的幂（那样 17 行得陪补 15 行空行），而是在相邻两个 2 的幂中间插了一档半程档（6、12、24、48……）。客户端并发充足时，稳态下几乎趟趟直接打满天花板那一档，中间的小档位只在刚启动、收尾或低谷时才用得上。
  • 行长档 Lb：本趟最长那条问题行归入的 8 等分档位（我们三道题分别是 1024 / 768 / 320）。
  • 状态长档 Sr：本趟最长那条查询长度向上取 2 的幂（24 token 取 32）。

三维组合太多，启动时录不完，kev 只能反过来——运行期第一次撞见某个规格先逐个发射跑过去，同一规格跑热了再停下来花 0.4 秒录成图，图攒多了就把最久没用的淘汰掉。

  • 默认真正卡脖子的不是 GRAPH_ROWS = 32，而是面积预算 GRAPH_TOKENS = 32768：跑 913 token 那道题时，每行总宽 32 + 1024 = 1056，32768 ÷ 1056 = 31，对齐行数档位后落到 24 行——哪怕队列一次抓来 64 条请求，也得拆成 3 趟跑。
  • 四个容量参数必须成套联动调：只拉大 MAX_BATCH 会拆成更多趟（外层还有 GRAPH_STATES = 16 先按 16 条请求切块）；只拉大 GRAPH_ROWS 会被面积预算拦住；把面积和状态槽一起拉大后才会真正推高单趟行数。
  • 切到「假设题面改长到 1100 token」：Lb = 1280 > 1024，整张图不复存在，64 条请求当场退回逐条串行（原因见下方误区）。
常见误区：题面超了 1024 只是进不了图，难道不会在图外自己按长度合批吗？ 真不会——长度归类只写在图模块门里面，门外没有备用合批；而且一题超长，同请求里没超标的短题也会连坐退回逐条串行。

正常的推理引擎确实绝不该退化成串行，但 kev 的调度顺序是「先在门口按整条请求安检，过了安检才做长度归类」：

1. 门外压根没写备用合批：按长度归类分桌的逻辑只住在图模块内部，而且绑死在启动时按 1024 宽一次性划好的固定缓冲上。1100 宽的行物理上塞不进这块缓冲，门外又没另写第二套动态分配显存的跨请求合批，被拦下的请求直接掉进单条 for 循环（作者注释原话：the rest, one at a time）。

2. 一题超长，全请求连坐：门口安检看的是「这条请求里最长的那道题 ≤ 1024」。哪怕只把题一从 913 改到 1100，明明只有 698 和 271 的题二、题三也会跟着整条请求被踢出门外；600 条请求共用题面，一超就是全军覆没——64 条请求一条接一条单跑 64 轮（每轮内含状态 1 趟 + 问题 1 趟，实打实 128 趟前向）。

3. 对比「查询超长」更能看出是题面侧没写兜底：如果超长的是用户的查询（比如 1,500 token，超过 GRAPH_STATE = 1024 但未超状态槽宽度 BANK_WIDTH = 4096），代码倒专门做了挽救——先把这条长查询单独算完塞进状态槽，后面的三道问题行照样合批跑图；唯独题面超 GRAPH_ROW = 1024 没有任何兜底。这和第 07 节「关图顺带关掉合批」是同一个病根，所以将来只要加长题面，必须同步上调 GRAPH_ROW。

发车时机：不凑数、不等点，以及实测抓到的「1 + 3」现象

有了批次上限 MAX_BATCH，服务线程什么时候发车？答案是完全按「上一趟什么时候跑完」走，一毫秒都不傻等凑数：

  • GPU 闲着时：门口队列只要进来 1 条请求，当场发车，不设任何「再等几毫秒看有没有第 2 条」的凑批定时器——所以低并发下零额外等待延迟。
  • GPU 正忙时：上一趟跑的那几十毫秒里，新到的请求自然在队列里排队；上一趟刚算完、GPU 腾出手的瞬间，回头看一眼门口此刻攒了多少条，一把全捞走（最多捞 MAX_BATCH 条）立刻发下一趟——攒了 5 条就捞 5 条（补到 6 行档），攒了 50 条就捞满 MAX_BATCH 条。
实测抓到的「1 + 3」交替现象：当客户端并发恰好等于 MAX_BATCH = 4 时，我们在耗时分解日志里亲眼看到服务全程按 1 条、3 条、1 条、3 条 交替发车，永远吃不满 4！原因正出在这套发车规则上：第 1 条先到半步，趁 GPU 空闲被单独捞走开跑；剩下 3 条在它跑的那几十毫秒里陆续到齐，等它跑完被合成一趟 3 条（还得补 1 行空行凑够 Nb = 4 的图！）发走；而最早跑完的那 1 个客户端此时刚收到响应并发出下一条，又恰好赶在 3 条跑完时排在队首——从此严丝合缝锁死在 1 + 3。所以压测或线上喂流时，客户端并发必须明显高于单趟批上限（例如批上限 4 配并发 8–16，批上限 32 配并发 64），门口队列才有富余把每一趟真正喂满。
常见误区：队列积压起来之后，kev 到底会不会按长度分类凑批？ 分两截看：门口大队列纯按先来后到抓前 MAX_BATCH 条，不跨批挑长短；抓进来的这一批内部只要 ≤ 1024，会做两道从短到长的排序归类。

把从排队到前向拆成三步，哪一步分、哪一步不分就一目了然了：

1. 门口大队列：纯先来后到，不挑长短。哪怕队列里已经积压了 200 条请求，服务线程也不会去这 200 条里挑长度相近的凑一锅，而是直接按到达顺序抓走队头前 MAX_BATCH 条。

2. 抓进来的这一批内部（≤ 1024 的正常请求）：做了两道按长度排序归类。过了 1024 安检的那批请求进来后会重排两次——先按「查询长度」从短到长排，用动态规划切成每桌最多 GRAPH_STATES（默认 16）条，短查询不会去陪长查询补齐；再把同桌的所有「问题行」打散，按「题面长度」从短到长排，把 271、698、913 各自归成独立的一趟。这也是调大 MAX_BATCH 的隐性好处：一次抓进来的池子越大，内部排序分桌越容易凑齐同长度。

3. 题面 > 1024 的超限请求：连第 2 步的门都进不去。安检发生在第 2 步之前，超标的请求在门口就被踢进单条循环了，压根走不到里面那两道排序归类。

05十个超参怎么看：准入、容量、管理

所有能调的旋钮就这十个。按职责分成三类后，调哪个安全、调哪个有悬崖一目了然。

参数默认值管什么类别
GRAPH_ROW1024单条问题行归档后的最大长度，超了整条请求不走图准入
GRAPH_STATE1024单条查询状态的最大长度（前缀缓存未命中时）准入
BANK_WIDTH4096前缀缓存命中时允许接纳的最大状态长度，也是每个状态槽的固定宽度准入
MAX_BATCH64服务线程每次从请求队列最多抓几条一起处理容量
GRAPH_ROWS32单趟问题行图最多允许几行容量
GRAPH_TOKENS32768单趟「行数 × (状态宽 + 行宽)」的总面积上限容量
GRAPH_STATES16状态槽个数，即一趟最多同时暂存几条不同查询的状态容量
HOT_BUCKET3同一规格先逐个发射跑满几次后，忙时也值得停下来录成图管理
GRAPHS_KEPT256最多缓存几张已录好的图，超了淘汰最久没用过的那张管理
PASS_TOKENS256按长度分组时的每趟固定起步成本常数（不是长度上限）管理
  • 准入类决定「谁能进图」：不动它们，支持的最大输入长度就不变；一旦数据变长跨过它们，不会报错，只会静默掉回串行慢路。
  • 容量类决定「一趟塞多少」：纯粹是吞吐与显存之间的旋钮——把容量调小或调大，绝不会收窄模型能接受的输入长度。
  • 管理类是三维规格逼出来的独有产物：vLLM / SGLang 在启动时就把图全录完了，所以压根没有 HOT_BUCKET 和 GRAPHS_KEPT 这两个概念；kev 把启动耗时省下来，摊到了服务刚起来的前几十条请求上。
别把「超参」和「每趟规格 Nb / Lb / Sr」混为一谈 表里十个是你设的封顶值；Nb / Lb / Sr 是每来一批请求现场算出来的档位，没法手动指定。

服务线程不需要任何标定集：队列里抓到哪几条请求，就按这几条的真实长度算出本趟的 Lb（受 GRAPH_ROW 封顶）、Sr（受 GRAPH_STATE / BANK_WIDTH 封顶）和 Nb（受 GRAPH_ROWS 与 GRAPH_TOKENS ÷ (Sr + Lb) 较小者封顶）。在我们的评测集上，最长那道题固定跑在 (Nb ≤ 24, Lb = 1024, Sr = 32)。

07我们在 P800 上踩出来的两个真坑

把 kev 迁到昆仑芯 P800 时摔过的两跤——都不是参数没调优，而是把架构耦合与跨卡数值假设想当然了。

第一跤：以为只关了图，其实把跨请求合批一起关没了

刚上 P800 时，出于「非英伟达卡先别碰 CUDA Graph」的保守心理，我们把图开关设成了关闭（KEV_CUDA_GRAPHS=0）。测出来的吞吐是一条死平的直线：并发 1 是 8.78 req/s，拉到并发 32 还是 9.12 req/s，客户端延迟随并发整倍放大（0.11 → 0.44 → 1.75 → 3.49 秒）——典型的单车道排队。

追查后发现：主流引擎（vLLM / SGLang）的合批调度器与图完全独立，就算设了 enforce_eager=True 关掉图，多条请求照样合批跑；但 kev 的跨请求合批只实现在图模块那套二维缓冲里。关掉开关意味着连图管理对象都不创建，所有请求当场退回一条接一条串行算。把开关改回开启（P800 的兼容层直接跑通了图录制，录下 52 张、0 失败）、配 MAX_BATCH = 4，吞吐立刻跳到 17.99 req/s（1.97×）。

拆开量清这 1.97 倍到底谁出了多少力：保留图模块对象（保住跨请求合批缓冲）但禁止录图后，并发 32 下「仅合批、不录图」就已经从 8.97 冲到了 15.81 req/s（1.76×），再打开图重放推到 18.02 req/s（相对纯合批再 +14%）——那一倍提速里四分之三来自合批、四分之一来自图重放。更有意思的是把批上限拉到 32 之后，仅合批已达 18.49 req/s，图重放只剩 18.78 req/s（+1.6%）：单趟塞满 25 条请求后 GPU 已被计算喂饱，派活空隙自然消失，完美印证了第 01 节的前提。

第二跤：「答案与同批邻居无关」在换硬件后不自动成立

前面说过，只要 padding 屏蔽精确，同一条请求不管自己单独跑还是跟 31 条别的请求拼在一批跑，输出应该完全一致——H20 上实测确实零翻转（522/600）。

但搬到 P800 后，把 MAX_BATCH 放到默认 64 时准确率从 523/600 掉到了 522/600；即便压回 MAX_BATCH = 4 保住标签不翻，并发 4 / 16 / 32 下的预测概率仍有最高 0.0177 的浮动。根源在于底层矩阵乘与归约算子在不同批尺寸下走了不同的浮点累加顺序，压小批上限只是收窄了暴露面，并没有根除随负载漂移的现象。

追查那 1 条翻转样本：掉回 522 丢掉的其实是一次「走运的舍入」 所有掉到 522 的配置翻的都是同一条阈值边缘样本——它在 H20 上本来就是答错的。

把各个变体在 600 条样本上逐条对齐后发现，凡是掉到 522 的实验臂，多错的永远是同一条压在决策边界上的样本。而这条恰好也是 P800 相对 H20 唯一不同的样本——H20 上它答错（522/600），P800 在小 batch 下因浮点舍入差异碰巧跨过阈值答对了（523/600）。

也就是说，拿「不低于 523」当硬红线，相当于要求新配置必须保住一次偶然的舍入运气。真正站得住脚的上线准则应当是「同一配置在不同并发下逐条输出一致」，而不是死守单条边界样本的 0.17 个百分点。
