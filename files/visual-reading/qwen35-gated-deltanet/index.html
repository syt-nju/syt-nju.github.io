从零看懂 Qwen3.5 / 3.8 的 Gated DeltaNet：记忆机制、Cache 变化与推理快慢的真相

给不熟悉线性注意力的后训练工程师：把「固定状态矩阵」拆开看懂，再算清长 Decode 到底靠什么提速、Prefill 究竟会不会成为卡点。

适用范围：Qwen3.5 全系 & Qwen3.8 主线（27B / 2.4T-A95B，共用同一套 GDN 混合骨干） 核心论文：Gated Delta Networks（ICLR 2025） 对照口径：以 Qwen3.5 / 3.8-27B（64 层）精确配置核算

30 秒先拿走核心结论

1. Gated DeltaNet（GDN）是什么：它把标准 Attention 越攒越长的「历史 K/V 清单」，换成了一本固定页数的记忆矩阵（状态 S）。每来一个新 token，先按「遗忘门」衰减旧记忆，再拿当前 Key 试读旧值、只写入新旧值的误差（Delta 规则）——解决传统线性注意力「反复累加会写糊」和「切换话题清不掉」两个老毛病。

2. Cache 怎么变：Qwen3.5 / 3.8 把 75% 的层换成 GDN（每 3 层 GDN 配 1 层完整 GQA）。Cache 从「全靠长度 L 线性膨胀」，变成「固定底薪（27B 48 层共 146.8 MiB，需 FP32 保存）+ 1/4 的 KV Cache」。小于 783 token 时甚至比纯 GQA 更占显存，超过 32K 才省出近 4 倍空间；同时前缀缓存（Prefix Caching）不再免费。

3. 长 Decode 为何更快：Decode 卡在显存带宽而不是算力。短序列单请求时，GDN 并不会神奇加速；真正生效的逻辑是长上下文时单请求显存缩水近 4 倍 → 单卡能塞下的 Batch Size 放大近 4 倍 → 读一次模型权重能分摊给更多并发序列，再叠加 75% 的层无需扫描长 KV。

4. Prefill 会不会卡：朴素逐 token 递推确实会惨慢，但现代推理引擎用分块并行（Chunkwise Parallel，通常 64 token 一块）把块内更新打包成稠密矩阵乘喂满 Tensor Core。结果是：短 prompt（<4K）略慢 5%–10% 且极度依赖融合算子；超长 prompt（32K–256K）反而因 O(L) 完胜全注意力的 O(L2)。

01从零看懂 Gated DeltaNet：把「翻记录」变成「改笔记本」

不需要懂状态空间模型或 Mamba，只要顺着你已经熟悉的 Softmax Attention 走三小步，就能把 Gated DeltaNet 的核心机制看透。

在标准 Transformer 里，每一层 Softmax Attention（全注意力） 像一个严谨但笨重的档案员：上下文每多一个 token，它就把对应的 Key 和 Value 抄进档案袋（KV Cache）。等到第 t 步需要查信息时，它拿着当前 Query 把档案袋里前面 t 张卡片从头到尾全翻一遍，按相似度加权求和。这样做的好处是记忆无损，缺点是上下文越长，档案袋越厚、每次翻找越慢。

Linear Attention（线性注意力）换了一个完全不同的思路：不再保留每一张历史卡片，而是只维护一张固定大小的矩阵状态 S（可以想象成一本固定页数的「键值速记本」）。每来一个新 token，就把它的 (Key, Value) 写进这本速记本；需要读取时，直接拿 Query 乘一下速记本 S 就算完——不管前面读了 1,000 字还是 200,000 字，速记本永远一样厚。

但最朴素的线性注意力（直接累加 St = St-1 + kt vtT）在真实语言任务里效果很差，因为它有两个致命硬伤：

  • 不能「覆盖更新」，越写越糊（Memory Collision）：假设代码里前面写过 port = 8000，后面又改成了 port = 8080。朴素加法不会擦掉旧值，而是把两次写入直接叠加，再查 port 时读出来的是混在一起的脏值。
  • 不能「一键清空」，旧话题占满页数：速记本页数有限（单个头只有 128 × 128 的容量）。当对话从「修数据库 bug」切到「写前端样式」时，如果不赶紧把旧记忆淡化掉，新旧信息就会挤爆矩阵容量。

Gated DeltaNet（GDN）做的事情非常直白——它给这本固定速记本配齐了两个动作，正好一一补上这两个漏洞：

  • 动作 1 · 遗忘衰减门（Decay Gate, αt ∈ (0, 1)）：每来一个新 token，模型先根据当前内容决定把旧速记本整体保留多少比例。话题没变时 αt ≈ 0.99（几乎全留）；遇到任务切换或大段无关噪声时 αt → 0（瞬间清空）。
  • 动作 2 · 误差纠错写入（Delta Rule，步长 βt ∈ (0, 1)）：写新值 v 之前，先拿当前 k 从速记本里「试读」一次旧值 v̂ = SdecayedT k，算出差值（预测误差）v − v̂，再只把这份差值乘以写入强度 βt 写回速记本。如果旧值是 8000、新值是 8080，它只补写 +80，精准覆写而不叠脏。

展开看数学公式对照（只需 3 行，核对机制用） 对比朴素线性注意力、Mamba2 门控衰减与 Gated DeltaNet 单步更新方程的精确差别。

对单个头，设状态矩阵为 St ∈ Rdk × dv，当前输入经投影与归一化得到 qt, kt ∈ Rdk、vt ∈ Rdv，数据依赖衰减门 αt = exp(gt) ∈ (0, 1)，写入强度 βt ∈ (0, 1)：

  • 朴素线性注意力：St = St-1 + kt vtT（只加不删，必然撞车）。
  • Mamba2（仅衰减门）：St = αt · St-1 + kt vtT（能整体淡忘，但同 Key 写入仍会叠加）。
  • Gated DeltaNet：先整体衰减 S' = αt · St-1，再按预测误差做一次在线梯度下降更新：St = S' + kt · (βt · (vt − S'T kt))T，输出 ot = StT qt。

从在线学习视角看，St 就像一个在推理期间随时微调的「快权重（Fast Weight）」矩阵：每读一个 token，就对着回归损失 ½ ‖ST kt − vt‖2 走一步带权重衰减（αt）的 SGD，学习率就是 βt。

02为什么 Qwen3.5 / 3.8 不做成纯线性？3 : 1 混合排布拆解

既然 GDN 这么省显存，为什么 Qwen 团队没有把 64 层全部换成 GDN，而是固执地每 3 层插回 1 层全注意力？

答案还是物理容量上限。在 Qwen3.5-27B 和 Qwen3.8-27B 里，GDN 每个 Value 头的状态矩阵尺寸是 128 × 128——从线性代数上讲，它最多只能无损存放 128 个互相正交的键值对。一旦上下文拉长到几万 token，让模型去做逐字精确回查（比如从 10 万字日志里抄出一串 32 位随机 UUID，或者精准对比相隔很远的两段代码），纯线性模型依然会输给保存完整 KV 的全注意力。

因此，Qwen3.5 / 3.8 采用了「3 层 GDN 负责低成本压缩主干 + 1 层 Full GQA 负责周期性精确回查」的 3 : 1 混合配方：在 27B 模型的 64 层里，重复 16 个 [GDN → GDN → GDN → Full GQA] 大块（共 48 层 GDN + 16 层 Full GQA）。

另外注意一个关键细节：每个 GDN 层内部（1/4 的 Full GQA 层没有）在 QKV 线性投影之后、进入 Delta 核心之前，会经过一层核宽 K=4 的深度因果短卷积（Depthwise Causal Conv1d + SiLU）。它把当前 token 的原始投影 u[t] 和缓存里最近 3 步的原始投影 u[t−3..t−1] 逐通道加权融合（Q、K、V 各自独立卷积，互不交叉），整理出最终的 qₜ, kₜ, vₜ，再送进 Delta 核心——先用 kₜ, vₜ 更新状态 S，再用 qₜ 读出当前输出 oₜ。

  • Full GQA 层怎么配合：16 层全注意力不走短卷积，直接做带输出门控的 Gated GQA（24 Q / 4 KV，头维 256，Partial RoPE 64/256），兜住跨数万 token 的精确检索底线。

03Cache 层面的变化：从「纯按长度计费」变成「固定底薪 + 1/4 浮动」

引入线性注意力后，推理引擎存的不再是一张单一的 KV Cache，而是异构的两套状态——这直接改写了显存占用曲线、交叉点与前缀缓存行为。

很多人对 Qwen3.5 / 3.8 的第一印象是「没有 KV Cache 了，显存恒定 O(1)」——这是不准确的。因为还有 25% 的 Full GQA 层，单条请求在显存里实际要占三样东西（以 Qwen3.5 / 3.8-27B 为例）：

  • ① GDN 循环状态矩阵 S（固定，48 层合计 144.0 MiB）：每层 48 V头 × 128 × 128 × 4 字节（FP32） = 3.00 MiB。无论上下文是 100 token 还是 262,144 token，永远占这么多。
  • ② GDN 短卷积滑窗状态（固定，48 层合计 2.81 MiB）：核宽为 4 的因果卷积只需要记住最近 3 个 token 的投影输入（3 × 10,240 × 2 字节 BF16 = 60 KiB/层），几乎可忽略。
  • ③ Full GQA 的 KV Cache（随长度 L 增长，16 层合计 64 KiB / token）：每层 2(K/V) × 4 KV头 × 256 维 × 2 字节（BF16） = 4 KiB/token。对比同等深度与 GQA 宽度的 64 层纯 Transformer（256 KiB/token，刚好与 Qwen3-32B 相同），增长斜率直接砍掉 75%。

把这三项加起来，你会发现一个非常反直觉的算术事实：单条请求长度短于 783 tokens 时，混合架构的 Cache 反而比纯 Transformer 更占显存！拖动下面的滑块，亲自看一遍从 512 token 到 256K 的显存与单卡并发变化：

除了显存大小，Cache 的工程行为还有 3 个深层变化

如果你平时在用 vLLM / SGLang 跑 rollout 或线上服务，下面这三点往往比「省了多少 GB」更容易踩坑：

变化 1 · Prefix Caching（自动前缀缓存）不再「免费且任意切分」
KV Cache 是追加列表，天然支持任意前缀复用；GDN 状态是原地覆写的，跑到后面就把前面覆盖了。

在纯 Transformer 里，两条请求如果共享前 4,000 token 的系统提示词，引擎只要把前 4,000 token 对应的 KV 显存块标成共享只读，第 2 条请求直接从第 4,001 token 开始算——零额外显存拷贝。

但在 GDN 层里，状态矩阵 S 只有一份，处理到第 4,001 token 时，它是直接在原矩阵 S 上原地覆写的。如果不额外留一份拷贝，第 4,000 token 那一刻的状态就永久丢失了，无法回退。因此：

  • 推理引擎要么按固定步长额外存「状态快照检查点（checkpoint）」，用更多显存换前缀复用；
  • 要么在不支持状态对齐的场景下干脆关掉前缀缓存（这也是混合架构在 vLLM/SGLang 中实现前缀缓存明显晚于纯 Attention 的原因）。
变化 2 · GDN 状态必须锁死 FP32，不能随便压成 BF16 / FP8
KV Cache 彼此独立，压成 FP8 只影响单个 token 精度；GDN 状态要经历上万次连续递推，低精度会滚雪球漂移。
展开 ▸

标准 KV Cache 里，第 100 个 token 的 K/V 和第 10,000 个 token 的 K/V 各自独立存放，做 FP8 量化时误差不会跨步累积。

而 GDN 的状态矩阵 St 每一 token 都要乘一次衰减再做误差加减；如果把 St 降成 BF16（尾数只有 7 bit），微小的舍入误差会连续滚雪球几万步，导致长上下文生成乱码或检索崩塌。因此在 Qwen3.5 / 3.8 的官方配置里，mamba_ssm_dtype 明确锁死为 float32——这也是单层状态占到 3 MiB 而不是 1.5 MiB 的直接原因。

变化 3 · 内存调度从「纯 Paged KV」变成「双池混合管理」
引擎要同时管两块账：给 16 层全注意力按页动态分块，给 48 层 GDN 按并发条数预分配固定槽位。
展开 ▸

在纯 Transformer 服务里，你可以放心把最大并发数开很大（比如 256），因为短请求只占很少的 KV 页。但在混合架构里，每多接一条正在跑的请求，不管它多短，都要立刻为它划出 146.8 MiB 的 GDN 状态槽位。

所以调部署参数时，最大并发序列数（如 max_num_seqs）的显存成本变重了：如果设成 256 条并发，光 27B 的 GDN 固定状态槽就要先吃掉 256 × 146.8 MiB ≈ 36.7 GiB 显存，哪怕每条请求只有 100 个 token。

04长 Decode 提速的真正逻辑：不是「算得快」，而是「搬得少 + 批得大」

回到你最关心的问题：这套架构确实是为长上下文、长生成任务（如长思维链、多轮 Agent）设计的，但它的加速逻辑并不是「线性层计算更快」。

要看清 Decode 阶段为什么慢，先记住 GPU 推理的一条铁律：Decode 阶段几乎永远是显存带宽受限（Memory-Bandwidth Bound），而不是算力受限。

每吐出 1 个新 token，GPU 必须把 27B 模型的全部权重（BF16 约 54 GB）加上所有正在运行请求的缓存，从 HBM 显存完整搬进芯片算一次。现代加速卡的算力极高，但显存带宽有限——搬完这几十 GB 数据的功夫，算力单元其实只忙了不到 5%，其余时间全在等数据搬运。

有了这个前提，GDN 在长 Decode 上生效的两级真实逻辑一下子就清晰了：

  1. 单请求维度（长上下文下省带宽，但短上下文不省）：每步 Decode 要搬的数据总量 = 54 GB 权重 + 本条请求的 Cache。在 2K 短文本下，Cache 只有几百 MB，相对 54 GB 权重几乎可以忽略，所以单条短序列的 Decode 速度，GDN 并不比纯 Transformer 快。只有当上下文涨到 32K–128K（纯 GQA 的 KV 膨胀到 8–32 GB，开始逼近甚至反超权重体积）时，把 75% 层的 KV 压成固定的 146.8 MiB 才会明显减少单步搬运量。
  2. 系统吞吐维度（真正的杀手锏——靠大 Batch 摊薄权重搬运）：单卡显存容量是死的（例如 96 GB）。在 32K 上下文下，混合架构因为省出了近 4 倍缓存空间，能让单卡同时跑的并发数从 4 条直接翻到 16 条。同样从 HBM 搬一次 54 GB 权重，纯 GQA 一次只推进 4 个 token，混合架构一次推进 16 个 token——分摊到每条请求的权重搬运成本直接打 2.5 折！
交互对比：不同场景下，每产出 1 个 Decode Token 需要从 HBM 搬运多少数据？
切换三个典型场景：直观对比「短上下文单请求」「超长上下文单请求」与「长上下文高并发满载」下，GDN 的真正提速倍数从何而来。
展开说明 ▸
  • 场景 1（2K 短文 · Batch=1）：每步搬运量 99% 都是 54 GB 权重，两种架构的每 token 搬运量相差不到 1%——印证了「短序列单条 Decode 几乎感受不到线性层优势」。
  • 场景 2（128K 长文 · Batch=1）：纯 GQA 的 KV 膨胀到 32 GiB，单步总搬运量涨到 ~88.4 GB；混合架构只需搬 ~62.7 GB（权重 54 GB + 缓存 8.14 GiB），单用户生成速度提升约 1.4×。
  • 场景 3（32K 长文 · 96 GB 单卡满并发）：纯 GQA 最多塞 4 条，每条分摊 13.5 GB 权重 + 8 GiB KV = 22.1 GB/token；混合架构能塞 16 条，每条仅分摊 3.38 GB 权重 + 2.14 GiB 缓存 = 5.68 GB/token——整卡吞吐拉开 3.9×！如果换成 397B-A17B / 2.4T-A95B 这类激活参数更小的 MoE 模型，权重基数更小、Batch 放大更猛，Decode 吞吐优势甚至能拉到 8× 以上。

05那线性层在 Prefill 时容易成为卡点吗？分块并行与真实拐点

你的直觉非常敏锐：看第 1 节那个「必须算出 St-1 才能算 St」的递推公式，任何人第一反应都会问——这在 Prefill 读几万字 Prompt 时岂不是只能串行、慢成蜗牛？

如果真按递推公式逐个 token 去跑，答案是：会的，而且会惨不忍睹。一次 4,096 token 的 Prefill 如果串行做 4,096 次小矩阵运算，Tensor Core 根本吃不饱，全耗在反复读写显存和算子调度上。

Gated DeltaNet 论文（以及 Qwen3.5 / 3.8 的推理内核）能把 Prefill 救回来，靠的是分块并行算法（Chunkwise Parallel）：

  • 切块：把长度为 L 的输入序列切成固定大小的小块（工程上通常选 chunk = 64 个 token）。
  • 块内全并行（喂满 Tensor Core）：利用线性代数里的 WY 紧凑表示，把块内 64 步前后依赖的 Delta 更新，先通过一次极小的 64 × 64 下三角求解整理好，然后全部转成高算术强度的稠密矩阵乘法，64 个 token 一步并行算完。
  • 块间才串行传状态：只有每过 64 个 token，才把块末的最终状态 S 交给下一块。原本 L 步串行被压缩成 L / 64 步，4,096 token 只需跨块接力 64 次。

直说结论：什么情况下 GDN 在 Prefill 时「真会成为卡点」？

把理论算量和真实硬件落地合在一起看，Prefill 阶段存在三个截然不同的区域——不能一概而论地说它快或慢：

场景 / 长度区间 线性层是卡点吗？ 真实原因与工程现象
没有融合算子
（纯 PyTorch / 未启用 FLA 或厂商 kernel）		 是严重卡点 GDN 多了短卷积、L2 归一化、门控、块内三角求解等一串细碎操作。若不融合，每层会碎成大量小 kernel 反复读写显存。例如我们在昆仑芯 P800 上实测 0.8B 混合模型时，未融合前逐元素/短卷积/GDN 吃掉 41.9% 前向耗时；换上厂商融合算子后吞吐直接翻倍。
短到中等 Prompt
（512 – 4K，已有融合算子）		 略拖后腿（慢 5–10%） 短序列下全注意力的 O(L2) 还没发威（整模型 90% 耗时都在 FFN 与线性投影里）。GDN 省下的 FLOPs 微不足道，反而多付了短卷积、三角求解和跨块接力的固定开销，实测 Prefill 吞吐往往比同尺寸纯 Attention 略低 5%–10%。
长到超长 Prompt
（16K – 256K，已有融合算子）		 不是卡点，反而是救星 跨过 16K–32K 后，全注意力层的 O(L2) 二次项迅速压过 FFN 成为绝对大头；而 GDN 保持严格线性 O(L)，单 token 耗时几乎不随长度恶化。256K 长文 Prefill 下，3:1 混合架构整体速度远快于同尺寸纯 Transformer。
一个容易被忽略的系统级 Prefill 边界：如果把多条变长请求首尾拼成一条长序列做 Continuous Batching，全注意力可以整条塞进静态 CUDA Graph；但 GDN 的分块并行需要按「请求分界点」切块——同样总计 8,192 个 token，不同长度组合切出的块数不一样，工作量锁不死，导致 vLLM 等引擎往往必须在 GDN 层把 CUDA Graph 断开（退回分段图或 Eager 模式）。在超大模型（27B）上影响较小，但在小模型（0.8B–4B）短请求高并发场景下，这笔 CPU 派活开销非常明显。

业务 / 训练负载 GDN 混合架构表现 核心原因
长思维链 / 多轮 Agent 长生成

超长文档阅读 / 问答
